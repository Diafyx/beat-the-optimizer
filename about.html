Beat the Optimizer

About

A daily puzzle for people who write SQL. Each level gives you a query, its tables and the statistics PostgreSQL planned with. You choose the join order, how each table is read and how each join is done. Your plan is then scored against the plan PostgreSQL 18 chose for the same query, under the same rules.

How a plan is scored

Every operator costs the rows it touches, counted on the real data, and a plan costs the sum:

  • a sequential scan costs the table's rows;
  • an index scan costs 4 per matched row, or 1 when the table is stored in the index's order;
  • a hash join or a merge join costs the rows of both inputs;
  • a nested loop costs the rows of one input times the rows of the other;
  • an index nested loop costs 4 per outer row and 4 per row it fetches;
  • a sort of n rows costs n × ⌈log2 n⌉;
  • every join also costs the rows it returns.

The best plan is found by trying every plan in the game's plan space, so “× best” on the result is exact. The cost model has the full rules and a worked example.

How PostgreSQL's plan was recorded

  • Each level's data is synthetic, generated from a seed, so it is the same every time it is built.
  • It is loaded into PostgreSQL 18 and analysed, with a statistics target large enough to read every row. Some levels then change data after ANALYZE, as happens between statistics runs on a real database.
  • Parallel workers and JIT are off, and every cost setting is PostgreSQL's default, so the plan is the same on every run.
  • EXPLAIN records the plan PostgreSQL chose. A bitmap heap scan or an index-only scan counts as an index scan on the same index, and a hash, materialize or memoize step belongs to its join.
  • The game then scores that plan with its own rules, on the true row counts, like yours.

Where the cost model differs from PostgreSQL's

PostgreSQL prices a plan in page reads and CPU work, from the row counts it estimates. The game counts rows touched, from the row counts that are really there. So PostgreSQL's plan can lose for two reasons: its estimates were wrong, which is what most levels are about, or the two cost models weigh the same plan differently.

The game's model is deliberately small. It leaves out:

  • pages, row width, caching and memory: hash tables and sorts never spill to disk;
  • CPU costs for operators and expressions;
  • partial order: an index scan costs 4 per row unless the table is stored exactly in the index's order;
  • plans that are not left-deep, cross products, parallel workers, bitmap scans that combine several indexes, and LIMIT;
  • queries over more than three tables.

Beating PostgreSQL here means your plan touches fewer rows. It does not promise that the plan would run faster on a real server.
